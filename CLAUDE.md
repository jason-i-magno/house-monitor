# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

A web app, run at home, that shows live temperature and humidity for each room. A Python backend (`housemon/`, **standard library only** but for `bleak`, Python 3.10+) collects readings, stores them in SQLite and pushes them to a plain HTML/CSS/JavaScript page (`housemon/web/`, with no build step, framework or CDN scripts). Readings come from simulated sensors, but for the rooms a house file gives an ecobee sensor, read from ecobee's cloud once signed in (`ecobee.py`, standard library too), and for those it gives a Govee H5075, heard over Bluetooth (`govee.py`) with `bleak`, the one third-party dependency (`requirements.txt`) and an optional one: without it those rooms stay simulated, and the tests don't need it. A MOVA robot vacuum's state and battery come from MOVA's cloud once signed in, as ecobee's readings do (`mova.py`, standard library too). A litter box the house file names a Litter-Robot for shows that robot's state, read from Whisker's cloud once signed in (`whisker.py`, standard library too), and simulated until then. Don't add others unless asked. There is no linter, formatter or packaging config for the Python; `tsconfig.json` only has TypeScript check the page's JavaScript, typed in JSDoc comments. A Go service in `cloud/` (Go 1.27, `go.mod` at the root, pgx its one dependency) is the cloud side, being built: it takes readings from houses over HTTP, keeps them in Postgres, and serves each house's page, the same files (see [Cloud service](#cloud-service-cloud)).

## Houses and `private/`

The simulator models a house file: a module with `HOUSE` (its rooms as `SimulatedRoom`, each sensor with its plan), `AREAS` (the parts with no sensor) and `DETAILS` (what the detailed view draws, or None). `house.load()` picks `--house`, else `private/house.py` if it exists, else `housemon/example_house.py`, a made-up house; the startup line says which. The server holds it as a `HouseFile`, which loads it again when it changes on disk, checked each time the page loads `/api/sensors`, so edits to a house file need only a page reload too; one that doesn't load, as while it's half edited, logs its error to stderr and leaves the last house in place. A room added that way has no history until its readings come in.

`private/` is the owner's real house, a separate private repo cloned into this one's ignored `private/` folder, with its own `house.py` and tests. Never commit it here, copy its rooms, sizes, colors or details into this repo, or describe them in code, comments, docs, commits or PRs. Changes to the real house are made, and committed, in `private/`'s own repo. This repo's code, tests and docs use the example house.

`tests/test_house.py` checks what every house file must get right, once per house as subtests: the example, and the private house when it's there, against its walls and details as the server sends them (`layout.py`). `tests/test_layout.py` checks the wall rule itself on small made-up layouts. Checks of one house in particular live with it: the example's in `tests/test_simulator.py`, the private house's in `private/test_house.py`, which `python3 -m unittest` finds too.

`--host 0.0.0.0` serves the whole network with no login, so keep it off the internet.

`data/` (gitignored) holds the user's readings, one database per source (`data/<source>.sqlite3`), and their ecobee, Whisker and MOVAhome sign-ins (`data/ecobee.json`, `--ecobee`; `data/whisker.json`, `--whisker`; `data/mova.json`, `--mova`): refresh tokens, readable only by their owner, never a password. Run tests and experiments against a `--db` elsewhere rather than writing to or deleting it, and with an `--ecobee`, `--whisker` and `--mova` of your own, since a run with the user's sign-ins polls their accounts; a run with `bleak` installed only listens, so it can hear the house's Govee sensors. At startup an empty database is backfilled with `--backfill-hours` (default 24) of simulated history, but for rooms read from ecobee or Govee sensors. A database from before a reading could have no humidity is migrated in place when opened (`Store._allow_no_humidity`).

The server rereads `web/` files on every request, and the house file when it's changed, so page and house changes need only a browser reload; other Python changes need a restart. There are no frontend tests, only the type check, so check page changes in a browser, in light and dark mode and at phone width: `tools/shot.mjs` screenshots a running server's page with headless Chromium (`$CHROME`, else one on the PATH or Playwright's), with the simulator's readings hidden, the charts in any range, the map in any view, cut away to a level or with its trees hidden or in a season, turned, tilted and zoomed in on a room or thing by name, or full screen. The map's detailed view needs WebGL, which headless Chromium gets from SwiftShader with `--enable-unsafe-swiftshader`. `tools/scan.mjs` builds the detailed view's meshes in Node (`tools/model.mjs` runs `model.js` in a context of its own, the house from `--dump`) for every cut and four ways round, the whole house in each season too, and lists faces in one plane that would flicker; its known leftovers are a few same-colored seams in the private house's stair railings, and in the example a spruce trunk's top inside its needles and a sliver of the sunroom. `firefox --screenshot` captures at the load event, before the page's fetches finish, so its screenshots show empty charts.

## Architecture

```
source.run() ──publish──► Hub ──► Store.add()  (thinned, SQLite)
 (collector thread)        └────► a queue per open page ──► /api/stream (SSE) ──► app.js
```

`__main__.py` wires this together. The source runs on a daemon collector thread, and `HouseServer` (a `ThreadingHTTPServer`) handles each request on its own thread, including each open SSE stream for as long as the page stays open.

- **Source interface:** a source is anything with a `sensors` list of `Sensor(id, name, floor, plan, heated, outside)` and a `run(publish, stop)` that calls `publish(Reading)`, or `publish(LitterBox)` with a litter box's state, until the `threading.Event` is set. It may also have an `areas` list of `Area(name, floor, plan)`, the parts of the house with no sensor (a hall, say), which the map draws as outlines, and `details`, a `Details` (`details.py`): the doors, windows, vents, appliances, closets, roof and yard the map's detailed view draws, naming rooms as the sensors and areas do. `SimulatedSource` gets all three from the house file, and takes up new rooms between rounds when the house file changes. `/api/sensors` sends them (`server.house_json`), or null for no details: each plan with `sides`, its share of the wall on each side, and the walls' thickness as `wall` (`layout.py`), and the details with everything placed against a wall, or from or to one, resolved to plain numbers. A room or area that isn't a rectangle, like an L, has a tuple of plans, one per piece, which `/api/sensors` sends as a list. Only `SimulatedSource` has `backfill()`, but `__main__` calls it whenever the database is empty, so guard that when adding a real source (and add the source to `--source`'s choices).
- **ecobee** (`ecobee.py`): a room in the house file can name the ecobee sensor in it (`SimulatedRoom.ecobee`, the name the ecobee app shows, matched whatever its case), and the outside a thermostat, for the weather ecobee reports where it is (`SimulatedRoom.ecobee_weather`: the first of its forecasts, the conditions now, from a weather service, not a sensor at the house). With a saved sign-in, an `EcobeeSource` runs on a thread of its own beside the simulator, polling the account's thermostats every 180 s and publishing those rooms' readings, and the simulator leaves them out (`SimulatedSource.skip`, set from the house file again when it changes). ecobee no longer gives out developer keys, so it signs in as ecobee's web app does (OAuth with PKCE against `auth.ecobee.com`, a second factor's code if the account has one), asking only to read, as Home Assistant's integration has since 2026.3; it refreshes the access token as it expires and keeps a rotated refresh token. It polls gently (`polling.poll_gently`, as the MOVA source does): a failed poll is logged to stderr and tried again after 2, 5 and then every 10 minutes, or its interval if that's longer, until one works; a lapsed sign-in says to sign in again, once, and isn't tried again until the sign-in's file is written again, as signing in does, looked for every 10 s; and a name the account has no sensor by is warned of, with the names it has, once until it's matched again. `tests/test_ecobee.py` runs it all against a fake ecobee.
- **Govee** (`govee.py`): a room can name the Govee H5075 in it instead (`SimulatedRoom.govee`, the name it broadcasts, `GVH5075_` and the last four hex digits of its address, as `--govee-scan` lists it, matched whatever its case), beside an ecobee sensor or, outside, a thermostat's weather, if it likes (but not those two both, which raises): then the Govee's readings come while it's heard, and the ecobee's fill in once it's gone 2 minutes unheard (`unless_heard`, which wraps the ecobee source's `publish`), as with a dead battery or Bluetooth off. The H5075 needs no app, account or pairing: it keeps broadcasting its reading, in its manufacturer data under Govee's company id, 0xEC88, six bytes: a zero, three big-endian packing the temperature in tenths of a degree times 1000 plus the humidity in tenths of a percent (the top bit set below zero), the battery (its top bit set for an error, let go), and a zero (`decode`). With `bleak` installed (`govee.available()`), a `GoveeSource` runs on a thread of its own beside the simulator, which leaves those rooms out (`skip`), and while any room names a sensor listens on another, with its own asyncio loop (`scan_bluetooth`), asking BlueZ for every broadcast, since `bleak` has it drop repeats and a steady reading would seem to go quiet. Every 10 s each room gets the newest broadcast heard from its sensor since its last reading, timestamped when it was heard, with its battery and signal, so a sensor out of range gives none. A scan that fails, as with Bluetooth off, is logged to stderr and tried again a minute later; one that hears no Bluetooth device at all for 30 s (`Quiet`), as after its adapter is unplugged for a moment or reset, which stops it without an error, is started again at once, warned of once until a sensor is heard again; and a name not heard from for 5 minutes, counted from when the house file first named it or listening started, whichever is later, so one added while the server runs has its full time, is warned of, with the names heard, once until it's heard again. Without `bleak`, rooms that name a sensor say so at startup and stay simulated. `tests/test_govee.py` runs it against fake broadcasts.
- **Litter-Robot** (`whisker.py`): a litter box in the house file's details can name the Litter-Robot 3 Connect it is (`Fixture.whisker`, the name the Whisker app shows, matched whatever its case; one robot to a box, each box's name its own). Whisker has no public API, so it signs in as its app does, as Home Assistant's integration does through pylitterbot: Amazon Cognito's user pool, by SRP (`password_claim`: the password never leaves, only a proof of it), a second factor's code if Cognito asks; then a robot's state comes from Whisker's v2 API with the id token, under the user in its `mid` claim, with the app's API key. With a saved sign-in, a `WhiskerSource` polls the account's robots every 120 s on a thread of its own, publishing each box's state: its status code (`LITTER_STATUSES`: what it says, and whether it needs seeing to, as a full drawer or a fault does), its cycles since the drawer was emptied, and how full the drawer is, the cycles over the capacity the robot estimates, or fuller once its status says only two, one or no cycles are left, until it's next ready, as pylitterbot reckons it; a robot without power or its connection is offline, with when it was last seen. Until then the simulator makes one up (`litter_box_at`: a cat four times a day, each visit its cat sensor interrupted, a wait, then a clean cycle, the drawer emptied Sundays at 10 and almost full by then), and leaves out those Whisker reads (`SimulatedSource.skip_boxes`). It refreshes the id token as it expires, warns as ecobee does, and polls gently as ecobee and MOVA do (`polling.poll_gently`): backing off while polls fail, and leaving a lapsed sign-in alone until it's signed in again. `tests/test_whisker.py` runs it against a fake Cognito, which checks the proof by the server's half of SRP, and a fake API.
- **MOVA** (`mova.py`): with a saved MOVAhome sign-in (`--mova-sign-in`, which asks for the account's region, email and password), a `MovaSource` runs on a thread of its own, asking each robot vacuum on the account every 60 s, through MOVA's cloud, in one request of up to 15 properties (`WANTED`), what it's doing, its battery, its task, its error code, its dock's tanks, bag and detergent (`DOCK`), and the life left of the parts it counts down (`PARTS`), those it has, and while its task is a clean underway (`CLEANING`, paused or gone back to its dock partway too), in a second request, how far along it is, the minutes it's been at it and the square meters it's cleaned (`VacuumClean`), and publishing each as a `Vacuum` (`readings.py`) to `Hub.publish_vacuum`. That isn't a reading: the hub keeps only the latest from each, which `/api/sensors` sends as `vacuums` and `/api/stream` as a `vacuum` event, and the page shows each as a card after the rooms, its battery, what it's doing, an error with the warning icon, and flagged as a room is when it goes quiet, with a clean underway's progress, minutes and square feet and a gauge of it, and notes, each with the warning icon: its error or warning in words (`problem`, from `ERROR_TEXT`, the integration's English; `WARNINGS` are codes it carries on through, so not an error), what's wrong at its dock (`dock`), and its parts at `PART_LOW` (15%) or less, to replace or to clean (`parts`, `VacuumPart`). MOVA has no public API, so it signs in as the MOVAhome app does, as the community Dreame Vacuum integration for Home Assistant (MIT) worked it out: the app's client id and secret and password salt, the same for every user, its headers in its order and lower case (`post`, with `http.client`, so nothing is added), an MD5 signature over each request's params (`signed`), and once signing in names the account's region, language and country, a header of them encrypted with AES-128 under the app's key, with a small AES of its own (`aes_ecb`), checked against FIPS-197, since Python has none. The newest apps connect with a TLS handshake that integration copies byte for byte; this uses Python's, which MOVA's cloud has taken. It keeps a refresh token and the app's install hashes, made from the email, not the email; refreshes the access token when it's within 10 minutes of expiring or MOVA says it has; lists the account's vacuums hourly, or again after MOVA answers a poll with an error, not a network one; polls gently, as the ecobee source does, backing off while polls fail and leaving a lapsed sign-in alone until it's signed in again; and shows a vacuum its cloud can't reach as offline. `tests/test_mova.py` runs it against a fake MOVA cloud, and checks the bytes on the wire.
- **Units:** readings are stored and sent in the sensors' own units, °C and percent relative humidity (`Reading` in `readings.py`), and only `app.js` converts to °F. The simulator computes in °F internally and rounds its output to the sensors' resolution, 0.1 °C and 0.1 %. ecobee reports tenths of a degree Fahrenheit, converted to °C, to two places, as it comes in; an H5075 broadcasts tenths of a degree Celsius and of a percent, kept as they are. A sensor that reads only temperature, as an ecobee SmartSensor does, gives a humidity of None, stored as NULL: its card says it reads temperature only, its map label and readout show no humidity, and the humidity chart leaves it out.
- **Stored vs. latest:** `Store.add` keeps at most one reading per sensor per `--store-every` seconds, and its per-sensor clock resumes from the database after a restart. `add_many` stores everything, for backfills and imports. `Hub.latest()` holds the newest reading from each sensor whether or not it was stored; `/api/sensors` returns it. A litter box's state (`LitterBox` in `readings.py`) isn't stored at all: `Hub.litter_boxes()` holds each one's latest, which `/api/sensors` sends as `litter_boxes`, by name, for each litter box in the details that names a robot (null before its first), and `/api/stream` as an `event: litter-box`, beside the readings' plain messages. Each reading says whether the simulator made it up (`Reading.simulated`, a column of its own; a database from before it was there is migrated, a reading with a battery taken as the simulator's, as only ecobee's came without one), and `/api/history?simulated=0` leaves those out.
- **Threads:** all threads share one SQLite connection (WAL mode, `check_same_thread=False`), guarded by `Store._lock`. Each SSE client gets a bounded queue, and `Hub.publish` drops readings for a full queue rather than block the collector.
- **History buckets:** `/api/history?hours=N` picks a bucket of whole minutes, at least `min_interval`, that gives at most `HISTORY_POINTS` (500) points per sensor. `Store.history` averages each bucket, including its timestamp. `test_server.py` pins the resulting bucket sizes. On the page, a live reading is added to the chart only if it comes at least one bucket after the last point. A gap longer than three of a room's usual steps between points (their median), or three buckets if that's longer, breaks its line (`lineGap`), so a room ecobee reads every 180 s or so draws a line in a 6 h chart's 60 s buckets, and between gaps a line is a smooth curve through its points that never bends past one, so a peak or dip drawn is one read (`smoothPath`: monotone cubic Béziers, as d3's `curveMonotoneX` draws).
- **Types:** `app.js` and `model.js` are typed in JSDoc comments, which `tsc` checks, strict (`tsconfig.json`), and the page runs them as they're written. Keep it at no errors. The house as `/api/sensors` sends it is typed once, at the top of `model.js` (`House`, `Sensor`, `Reading`, `Details` and the rest, each named as the dataclass in `readings.py` or `details.py` it comes from), so a field added to one, or to `server.house_json`, is added there too. Type a new function as the others are, a one-line `@param` comment above it, and cast (`/** @type {T} */ (expr)`) only what you know, as an element that's there, not to quiet an error.
- **Static files:** only the paths in the `STATIC` whitelist in `server.py` are served, so a new file in `web/` needs an entry there, and in the cloud service's two lists too (`web.go`'s `go:embed` and `assetTypes` in `cloud/api/api.go`). The page's links and requests are relative (`api/sensors`, `style.css`), so it works at `/` here and under `/houses/{id}/` in the cloud service; keep them so.
- **Sensor order matters:** `/api/sensors` lists sensors in the source's order (the house file's `HOUSE` for the simulator). The page groups cards by `floor` in order of first appearance. Each sensor gets the color slot of its index (`--series-1` to `--series-8`, then the gray `--series-other`), so reordering sensors changes their colors.
- **The simulator is pure:** `reading_at(room, t)` depends only on the room and the time (the local time of day, plus noise seeded from the sensor id and `t // 30`), so the backfilled history matches the live readings. Keep it that way. `tests/test_simulator.py` looks the example house's rooms up by name and checks how they relate (the basement colder than upstairs, the office heater on in the afternoon but not at night), so renaming or retuning them means updating those tests.
- **Page (`app.js`):**
  - All state lives in one `state` object.
  - "Hide simulated" in the header, shown while any room's newest reading is the simulator's and kept per viewer in localStorage, leaves the simulator's readings out: each room keeps its newest reading as `latest` and shows it as `reading`, null for a room the simulator reads while they're hidden, so its card goes (and a level with none left), the map shows it with no reading, and the charts leave it out of their legends and load their history with `simulated=0`, which drops a room's made-up past too. Shown, a made-up reading's card says "Simulated" in place of its battery and signal. A litter box's made-up state goes the same way.
  - Below the levels, each litter box that names a robot has a card (`updateLitterBoxes`): its status, a warning sign beside one that needs seeing to, how full its drawer is, in words and a gauge, its cycles since emptied, and how old its state is, or for one offline when it was last seen.
  - `CHARTS` gives each chart its measure and rooms. Unheated spaces (`Sensor.heated` false, like the garage) and the outside get a temperature chart of their own, so their range doesn't flatten the rooms' lines; humidity charts every room that reads it. A room keeps its color in every chart. Each legend entry is a button that hides or shows its room's line in that chart, with Hide all / Show all at the end. The hidden rooms are kept per viewer in localStorage, and the scale, readout and table follow the rooms shown.
  - Each chart's `<svg>` is created once, since it holds the focus and pointer listeners. Its contents are redrawn on new data, on resize, and every minute so the time axis slides.
  - A history response for a range the user has since switched away from is dropped (`historyRequest`).
  - After the SSE stream drops, the page reloads sensors and history to fill the gap.
- **House map:** a floor plan per level, or a 3D view you can turn, with each room colored by its latest temperature, or a detailed view of the house as it looks.
  - The button beside the views makes the map full screen (`setMapFull`): the browser's own full screen where it has one for the page, else fixed over the page, which stops scrolling under it, as on a phone; Escape or the button again leaves it. Full screen, each view fills the height its plot has, the floor plan in however many columns show its floors largest, a touch drag tilts as well as turns, and the detailed view's list waits.
  - A sensor outside (`Sensor.outside`) has no plan or room. The map shows its reading in its top-right corner in every view, with the swatch of its temperature on the scale, and in the floor plan and 3D view tints its background with that color, mixed 30% into the surface so the rooms, at full strength, and the labels stand out. Inside the house's outline, the floor plan stays the surface color. The map leaves the sensor out of the rooms and the keyboard focus, and its card goes under the floor name alone, not "… level".
  - Rooms are placed by `Sensor.plan` (`Plan` in `readings.py`, in feet, with each floor's elevation above the main floor, a height at the ceiling's highest, 8 ft unless set, and for a sloped ceiling a `drop`: the wall it slopes down to and how much lower it is there), and areas by `Area.plan`. Unless every sensor has one, the map puts each floor's rooms in a row instead and leaves areas out.
  - The example house (`example_house.py`) is a two-story house over a basement: dining room, kitchen, living room and entry on the main floor, with a garage a step down on the right and a sunroom off the kitchen, its ceiling dropping to the back; two bedrooms, a bathroom and a guest room off a hall upstairs; and an office and utility room off an L-shaped family room in the basement. The garage is unheated, and an outside sensor reads the weather the simulator models (`outdoor_f`). The bathroom's humidity spikes at shower times (`SimulatedRoom.showers`), and the entry, hall, guest room and utility room have no sensors, so they're `AREAS`. Sprinklers water its lawns and front bed, run from a controller in the garage, and a Litter-Robot stands in the utility room. Sensor ids are stored with every reading, so renaming a room keeps its id. `test_house.py` checks every house's layout: nothing on a floor overlaps, and each floor is level but for a step down of up to a foot, as a garage is.
  - Colors are a gradient. The `--temp-0` to `--temp-6` tokens in `style.css`, blue and red arms in equal lightness steps around a neutral gray, flipped for dark mode, sit at `TEMP_STOPS` in `app.js`, 3 °F apart around 68.5 °F. `tempColor` blends a room's value, rounded to a tenth as shown, between its two nearest stops in OKLab, holding past either end; the legend's CSS gradient blends the same way (`in oklab`), so the two match. A label inside a room takes white or near-black, whichever has more APCA contrast on its color. The stops are read from the theme, and read again when it changes.
  - The 3D view is an orthographic projection from any direction: turned by `state.mapAngle` and tilted by `state.mapTilt`, from -90 (below) to 90 (above). Dragging turns and tilts it, though a touch drags only sideways, since swiping up and down scrolls the page; the buttons below it turn, tilt and reset it; and with the map focused, shift with the arrow keys turns it (left and right) and tilts it (up and down) `MAP_KEY_TURN` degrees a press, as the buttons' tooltips say, while the arrows alone step through the rooms or parts (`mapKey`). The floor plan doesn't turn, so there shift with the arrows steps through the rooms too. Plus and minus (or = and _, so plus needs no shift) zoom the detailed view `MAP_KEY_ZOOM` times a press, as the zoom buttons' tooltips say, but with ctrl or cmd they're left to the browser to zoom the page. It's sized to the house's bounding sphere, so turning or tilting neither zooms it nor changes the map's height. From below, rooms show their floors instead of their tops.
  - It's drawn back to front (`paintOrder`). Each axis that separates two boxes votes on which is nearer, the one on the viewer's side; when the votes disagree, the boxes can't overlap on screen and get no order, since ordering them by one axis made cycles that drew lower rooms over upper ones. A box with a sloped ceiling votes as if it were as tall as its ceiling's highest point.
  - A room or area in pieces is labeled once, and on the floor plan it's walled as one shape (`unionOutline`), its focus outline too.
  - A room's label goes on its first visible face; a room hidden from the current angle gets none. Areas are empty frames, and their names show only beside full labels, at the first visible spot clear of the rooms and other labels.
  - Focusing a room redraws only the focus layer, not the rooms, so the element under a tap stays put and the tap can focus the map.
- **Detailed view** (`model.js`): the house drawn with WebGL from the source's `Details`, turning and tilting with the 3D view. `modelScene` takes the house as `/api/sensors` sends it, and its colors, and needs nothing of the page (the geometry helpers it shares with `app.js`, `extent` and `ceilingOf`, live in `model.js`, which the page loads first), so tools can build it outside a browser; `pageModelScene` builds it from `state`.
  - It's colored like the things themselves, from the `--model-*` tokens in `style.css`, or a house's own in their place (`Details.colors`, light and dark), not by temperature, so it has no scale and the outside reading no swatch. Its rooms' readings are in the readout, and a litter box's state.
  - In a house file's `DETAILS`, each thing is either `known`, from photos of the house or someone who knows it, or a guess to correct; the readout and the list under the map say which, but for a made-up house (`Details.example`). Things in a room are placed from its plan's back-left corner (its first piece's), standing in any of its pieces or across them, an opening by its room's wall and its offset along it (or a shed's, naming the shed as its room, from the ground), and things outside on the plan, a fixture there standing on the ground or the top of a raised ground it's in, as a bed's, and a gas meter against the house's wall, or an attic vent high on it. ## Cloud service (`cloud/`)

The cloud side of house-monitor, being built (milestone 1: running end to end locally): a Go service that a house's uplink sends its readings to, in batches, and that serves each house's page as the Python server does. Collectors stay at home, in Python; the house's layout stays in Python too, and is uploaded as `--dump` prints it rather than ported.

```
uplink ──POST batch──► api.addReadings ──► store.AddReadings (Postgres, ON CONFLICT DO NOTHING)
                             └──► hub.Publish (only what was new) ──► a buffered channel per open page ──► /api/stream (SSE)
```

- **Layout:** `cloud/cmd/housecloud` (`serve`, `house add`, `house token`; the database from `DATABASE_URL`), `cloud/api` (the routes, listed at the top of `api.go`, and the stream in `stream.go`), `cloud/store` (Postgres, and its migrations), `cloud/hub` (fan-out), `cloud/house` (`Reading`, as `readings.py`'s, field for field, and its checks). The page is embedded from `housemon/web` by `web.go` at the module root, since `go:embed` can't reach up out of a package's directory, so a binary always serves the page it was built with.
- **Houses:** every house has an id from the start (`/houses/{id}/`), and the page and its API are served under it, the same API as `server.py`'s. Only a house marked public can be read; there's no signing in yet, so a private house is 404, as one that doesn't exist. The public URL is to show the simulated example house and nothing else, so never make a real house public. `/` redirects to `-default-house`.
- **Writes** take the house's ingest token (`Authorization: Bearer hm_…`), stored only as its SHA-256: it's 128 random bits, so a slow hash adds nothing. `PUT …/api/house` takes the house as `--dump` prints it, checked for a list of sensors with ids; `/api/sensors` is that with each sensor's latest reading put in, and `vacuums: []`.
- **Ingest is idempotent:** a reading's key is its house, sensor and time, to the microsecond (`timestamptz`), and a batch is one `INSERT … SELECT FROM unnest(…) ON CONFLICT DO NOTHING RETURNING`, so a batch sent again after a lost reply stores nothing twice, and only the readings it did store go to open pages. Each reading in a batch is parsed and checked on its own (`house.ParseReading`): a bad one is rejected, with its index and why, and the rest stored, since refusing the whole batch would have the uplink send it forever. At most `MaxBatch` (1000) readings and 1 MiB a batch; a reading more than `MaxSkew` (5 min) ahead of the server's clock is rejected, as it would stay a sensor's latest until the clocks met.
- **History** buckets as `server.py`'s do, and `TestHistory` pins the same sizes as `test_server.py`: `date_bin` from the epoch, as SQLite's `CAST(ts / bucket AS INTEGER)`, rounded as Python rounds them. `Latest` looks each sensor up down the primary key (a `LATERAL` join), not a scan.
- **Streams:** a page that falls `hub.Buffer` messages behind is dropped rather than skipped over: its stream ends, and the page reconnects and reloads the house and its history, as it does after any drop, so it ends up whole. On shutdown `api.Server.Close` (registered with `RegisterOnShutdown`) ends every stream, or they'd hold `Shutdown` until its timeout. There's no `ReadTimeout`, which would cut streams off; handlers that read a body set a read deadline, and a stream sets a write deadline before each write.
- **Migrations** are `cloud/store/migrations/NNN_name.sql`, applied in name order at startup, each in its own transaction under an advisory lock, so copies starting together migrate once. Never edit one that's been applied; add the next.
- **Tests** run against a real Postgres, each in a schema of its own (`storetest`), so they run in parallel and leave nothing behind; without `HOUSECLOUD_TEST_DATABASE_URL` they skip. A field added to `Reading` in `readings.py` is added to `house.Reading`, its checks, the `readings` table (a new migration) and `store`'s column lists.

## Chart conventions

Keep these rules when changing or adding charts:

- One measure per chart, never two y-axes.
- Series colors are the CSS tokens in `style.css`, assigned in fixed order. The order keeps neighboring colors distinguishable for colorblind readers. Dark mode has its own values, under `prefers-color-scheme`. Rooms past the eighth share the gray `--series-other`, told apart by dash pattern (`OTHER_DASHES` in `app.js`) in their lines and line keys.
- Identity is never shown by color alone: there's a legend, line keys beside room names, and a table view.
- The house map's colors encode temperature, not identity: each room is labeled with its name and value, the scale legend sits below, and the room cards are its table view.
- Text uses the text colors, never a series color.
- The status colors (`--status-good`, `--status-warning`) are only for status, and always come with a label or icon.
- Every chart has the hover readout, also reachable by keyboard (arrow keys, Escape).
