# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

A web app, run at home, that shows live temperature and humidity for each room. A Python backend (`housemon/`, **standard library only**, Python 3.10+) collects readings, stores them in SQLite and pushes them to a plain HTML/CSS/JavaScript page (`housemon/web/`, with no build step, framework or CDN scripts). Readings come from simulated sensors, but for the rooms a house file gives an ecobee sensor, read from ecobee's cloud once signed in (`ecobee.py`, standard library too). Real Govee H5075 Bluetooth sensors, read with `bleak`, are planned and will be the first third-party dependency; don't add others unless asked. There is no linter, formatter or packaging config.

## Commands

```sh
python3 -m unittest                                      # all tests, private/'s too if it's there
python3 -m unittest tests.test_store.StoreTest           # one class (append .test_name for one test)
python3 -m housemon                                      # serves http://127.0.0.1:8000/ with simulated sensors
python3 -m housemon --db <tmpdir>/house.sqlite3 --port 0 # a throwaway run: its own database, any free port (printed at startup)
python3 -m housemon --house housemon/example_house.py    # the example house, even with a private one there
python3 -m housemon --dump                               # print the house as /api/sensors sends it, and exit
python3 -m housemon --ecobee-sign-in                     # sign in to ecobee (it asks), save it to data/ecobee.json, list its sensors
node tools/scan.mjs [house file]                         # faces in the detailed view that would flicker, no server needed
node tools/shot.mjs --view detailed --level Main --top --room Kitchen out.png  # screenshot a running server's map (--help for more)
```

## Houses and `private/`

The simulator models a house file: a module with `HOUSE` (its rooms as `SimulatedRoom`, each sensor with its plan), `AREAS` (the parts with no sensor) and `DETAILS` (what the detailed view draws, or None). `house.load()` picks `--house`, else `private/house.py` if it exists, else `housemon/example_house.py`, a made-up house; the startup line says which. The server holds it as a `HouseFile`, which loads it again when it changes on disk, checked each time the page loads `/api/sensors`, so edits to a house file need only a page reload too; one that doesn't load, as while it's half edited, logs its error to stderr and leaves the last house in place. A room added that way has no history until its readings come in.

`private/` is the owner's real house, a separate private repo cloned into this one's ignored `private/` folder, with its own `house.py` and tests. Never commit it here, copy its rooms, sizes, colors or details into this repo, or describe them in code, comments, docs, commits or PRs. Changes to the real house are made, and committed, in `private/`'s own repo. This repo's code, tests and docs use the example house.

`tests/test_house.py` checks what every house file must get right, once per house as subtests: the example, and the private house when it's there, against its walls and details as the server sends them (`layout.py`). `tests/test_layout.py` checks the wall rule itself on small made-up layouts. Checks of one house in particular live with it: the example's in `tests/test_simulator.py`, the private house's in `private/test_house.py`, which `python3 -m unittest` finds too.

`--host 0.0.0.0` serves the whole network with no login, so keep it off the internet.

`data/` (gitignored) holds the user's readings, one database per source (`data/<source>.sqlite3`), and their ecobee sign-in (`data/ecobee.json`, `--ecobee`): a refresh token, readable only by its owner, never the password. Run tests and experiments against a `--db` elsewhere rather than writing to or deleting it, and with an `--ecobee` of your own, since a run with the user's sign-in polls their account. At startup an empty database is backfilled with `--backfill-hours` (default 24) of simulated history, but for rooms read from ecobee. A database from before a reading could have no humidity is migrated in place when opened (`Store._allow_no_humidity`).

The server rereads `web/` files on every request, and the house file when it's changed, so page and house changes need only a browser reload; other Python changes need a restart. There are no frontend tests, so check page changes in a browser, in light and dark mode and at phone width: `tools/shot.mjs` screenshots a running server's page with headless Chromium (`$CHROME`, else one on the PATH or Playwright's), with the simulator's readings hidden, the map in any view, cut away to a level or with its trees hidden or in a season, turned, tilted and zoomed in on a room or thing by name, or full screen. The map's detailed view needs WebGL, which headless Chromium gets from SwiftShader with `--enable-unsafe-swiftshader`. `tools/scan.mjs` builds the detailed view's meshes in Node (`tools/model.mjs` runs `model.js` in a context of its own, the house from `--dump`) for every cut and four ways round, the whole house in each season too, and lists faces in one plane that would flicker; its known leftovers are a few same-colored seams in the private house's stair railings, and in the example a spruce trunk's top inside its needles and a sliver of the sunroom. `firefox --screenshot` captures at the load event, before the page's fetches finish, so its screenshots show empty charts.

## Architecture

```
source.run() ──publish──► Hub ──► Store.add()  (thinned, SQLite)
 (collector thread)        └────► a queue per open page ──► /api/stream (SSE) ──► app.js
```

`__main__.py` wires this together. The source runs on a daemon collector thread, and `HouseServer` (a `ThreadingHTTPServer`) handles each request on its own thread, including each open SSE stream for as long as the page stays open.

- **Source interface:** a source is anything with a `sensors` list of `Sensor(id, name, floor, plan, heated, outside)` and a `run(publish, stop)` that calls `publish(Reading)` until the `threading.Event` is set. It may also have an `areas` list of `Area(name, floor, plan)`, the parts of the house with no sensor (a hall, say), which the map draws as outlines, and `details`, a `Details` (`details.py`): the doors, windows, vents, appliances, closets, roof and yard the map's detailed view draws, naming rooms as the sensors and areas do. `SimulatedSource` gets all three from the house file, and takes up new rooms between rounds when the house file changes. `/api/sensors` sends them (`server.house_json`), or null for no details: each plan with `sides`, its share of the wall on each side, and the walls' thickness as `wall` (`layout.py`), and the details with everything placed against a wall, or from or to one, resolved to plain numbers. A room or area that isn't a rectangle, like an L, has a tuple of plans, one per piece, which `/api/sensors` sends as a list. Only `SimulatedSource` has `backfill()`, but `__main__` calls it whenever the database is empty, so guard that when adding a real source (and add the source to `--source`'s choices).
- **ecobee** (`ecobee.py`): a room in the house file can name the ecobee sensor in it (`SimulatedRoom.ecobee`, the name the ecobee app shows, matched whatever its case), and the outside a thermostat, for the weather ecobee reports where it is (`SimulatedRoom.ecobee_weather`: the first of its forecasts, the conditions now, from a weather service, not a sensor at the house). With a saved sign-in, an `EcobeeSource` runs on a thread of its own beside the simulator, polling the account's thermostats every 180 s and publishing those rooms' readings, and the simulator leaves them out (`SimulatedSource.skip`, set from the house file again when it changes). ecobee no longer gives out developer keys, so it signs in as ecobee's web app does (OAuth with PKCE against `auth.ecobee.com`, a second factor's code if the account has one), asking only to read, as Home Assistant's integration has since 2026.3; it refreshes the access token as it expires and keeps a rotated refresh token. A failed poll is logged to stderr and tried again next time; a lapsed sign-in says to sign in again; and a name the account has no sensor by is warned of, with the names it has, once until it's matched again. `tests/test_ecobee.py` runs it all against a fake ecobee.
- **Units:** readings are stored and sent in the sensors' own units, °C and percent relative humidity (`Reading` in `readings.py`), and only `app.js` converts to °F. The simulator computes in °F internally and rounds its output to the sensors' resolution, 0.1 °C and 0.1 %. ecobee reports tenths of a degree Fahrenheit, converted to °C, to two places, as it comes in. A sensor that reads only temperature, as an ecobee SmartSensor does, gives a humidity of None, stored as NULL: its card says it reads temperature only, its map label and readout show no humidity, and the humidity chart leaves it out.
- **Stored vs. latest:** `Store.add` keeps at most one reading per sensor per `--store-every` seconds, and its per-sensor clock resumes from the database after a restart. `add_many` stores everything, for backfills and imports. `Hub.latest()` holds the newest reading from each sensor whether or not it was stored; `/api/sensors` returns it. Each reading says whether the simulator made it up (`Reading.simulated`, a column of its own; a database from before it was there is migrated, a reading with a battery taken as the simulator's, as only ecobee's came without one), and `/api/history?simulated=0` leaves those out.
- **Threads:** all threads share one SQLite connection (WAL mode, `check_same_thread=False`), guarded by `Store._lock`. Each SSE client gets a bounded queue, and `Hub.publish` drops readings for a full queue rather than block the collector.
- **History buckets:** `/api/history?hours=N` picks a bucket of whole minutes, at least `min_interval`, that gives at most `HISTORY_POINTS` (500) points per sensor. `Store.history` averages each bucket, including its timestamp. `test_server.py` pins the resulting bucket sizes. On the page, a live reading is added to the chart only if it comes at least one bucket after the last point. A gap longer than `max(3 × bucket, 180 s)` breaks the line, and between gaps a line is a smooth curve through its points that never bends past one, so a peak or dip drawn is one read (`smoothPath`: monotone cubic Béziers, as d3's `curveMonotoneX` draws).
- **Static files:** only the paths in the `STATIC` whitelist in `server.py` are served, so a new file in `web/` needs an entry there.
- **Sensor order matters:** `/api/sensors` lists sensors in the source's order (the house file's `HOUSE` for the simulator). The page groups cards by `floor` in order of first appearance. Each sensor gets the color slot of its index (`--series-1` to `--series-8`, then the gray `--series-other`), so reordering sensors changes their colors.
- **The simulator is pure:** `reading_at(room, t)` depends only on the room and the time (the local time of day, plus noise seeded from the sensor id and `t // 30`), so the backfilled history matches the live readings. Keep it that way. `tests/test_simulator.py` looks the example house's rooms up by name and checks how they relate (the basement colder than upstairs, the office heater on in the afternoon but not at night), so renaming or retuning them means updating those tests.
- **Page (`app.js`):**
  - All state lives in one `state` object.
  - "Hide simulated" in the header, shown while any room's newest reading is the simulator's and kept per viewer in localStorage, leaves the simulator's readings out: each room keeps its newest reading as `latest` and shows it as `reading`, null for a room the simulator reads while they're hidden, so its card goes (and a level with none left), the map shows it with no reading, and the charts leave it out of their legends and load their history with `simulated=0`, which drops a room's made-up past too.   - `CHARTS` gives each chart its measure and rooms.   - A history response for a range the user has since switched away from is dropped (`historyRequest`).
  - After the SSE stream drops, the page reloads sensors and history to fill the gap.

## Chart conventions

Keep these rules when changing or adding charts:

- One measure per chart, never two y-axes.
- Series colors are the CSS tokens in `style.css`, assigned in fixed order. The order keeps neighboring colors distinguishable for colorblind readers. Dark mode has its own values, under `prefers-color-scheme`. Rooms past the eighth share the gray `--series-other`, told apart by dash pattern (`OTHER_DASHES` in `app.js`) in their lines and line keys.
- Identity is never shown by color alone: there's a legend, line keys beside room names, and a table view.
- The house map's colors encode temperature, not identity: each room is labeled with its name and value, the scale legend sits below, and the room cards are its table view.
- Text uses the text colors, never a series color.
- The status colors (`--status-good`, `--status-warning`) are only for status, and always come with a label or icon.
- Every chart has the hover readout, also reachable by keyboard (arrow keys, Escape).
